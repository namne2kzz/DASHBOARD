Biểu đồ Burndown & Burnup Chart

Theo dõi tiến độ Sprint / Release

Trục tọa độ

X

Thời gian (Ngày làm việc)

Mỗi điểm trên trục X là một working day từ ngày bắt đầu đến ngày kết thúc Sprint. Ngày nghỉ lễ/cuối tuần được loại trừ theo lịch của tổ chức.

Y

Đơn vị công việc — chọn một trong hai:

  • Remaining Hours — tổng giờ ước tính còn lại của tất cả Task chưa Done trong Sprint.
  • Story Points — tổng SP của User Story chưa "Accepted/Closed" trong Sprint.

Azure DevOps mặc định dùng Remaining Hours cho Burndown. Burnup dùng SP để thể hiện tổng scope & tổng hoàn thành cùng trục.

Công thức — Ideal Trend Line

// Burndown Ideal

IdealRemaining(d) = TotalWork × (1 − d / TotalDays)


// Burnup Ideal — scope line (flat) & done line (ramp)

IdealScope(d) = TotalWork // hằng số nếu không có Scope Change

IdealDone(d) = TotalWork × (d / TotalDays)

  • d — chỉ số ngày làm việc hiện tại (0-based, d=0 là ngày bắt đầu Sprint).
  • TotalWork — tổng giờ/SP khi Sprint bắt đầu (snapshot ngày 0).
  • TotalDays — tổng số ngày làm việc trong Sprint (loại trừ ngày nghỉ).

Thuật toán Back-end — Historical Data Snapshot

Bước 1 — Cron Job hàng ngày (EOD Snapshot)

-- Chạy lúc 23:59 mỗi ngày làm việc

INSERT INTO sprint_daily_snapshot (

sprint_id, snapshot_date,

remaining_hours, completed_sp,

total_scope_sp

)

SELECT

s.id,

CURRENT_DATE,

SUM(wi.remaining_hours),

SUM(CASE WHEN wi.state='Done'

THEN wi.story_points ELSE 0 END),

SUM(wi.story_points)

FROM work_items wi

JOIN sprints s ON wi.sprint_id = s.id

WHERE s.state = 'Active'

GROUP BY s.id;

Bước 2 — Vẽ đường Actual Remaining

API truy vấn bảng sprint_daily_snapshot theo sprint_id và trả về mảng (snapshot_date, remaining_hours) được sắp xếp tăng dần theo ngày.

Mỗi phần tử mảng là một điểm dữ liệu trên biểu đồ. Chart library (ECharts / Chart.js) nối các điểm thành đường polyline.

// Response shape

{ date: "2026-05-01",

remaining: 42,

completed_sp: 0,

scope_sp: 42 }

Bước 3 — Xử lý Scope Change

Khi Task/Story bị thêm vào Sprint giữa chừng → total_scope_sp tăng trong snapshot ngày hôm đó → đường Scope Line trên Burnup bậc nhảy lên.

Khi Task bị xóa / chuyển ra → total_scope_sp và remaining_hours giảm tương ứng.

Quan trọng: Hệ thống KHÔNG sửa lại Ideal Line khi có Scope Change — đường lý tưởng giữ nguyên theo TotalWork của ngày Sprint bắt đầu để PM nhận ra độ lệch so với cam kết ban đầu.

Cumulative Flow Diagram — CFD

Phát hiện nút thắt cổ chai

Thuật toán cộng dồn (Cumulative Count)

Mỗi ngày, hệ thống đếm số lượng Work Item đang nằm trong từng trạng thái tại thời điểm EOD. Đây là count tại điểm thời gian, không cộng dồn theo nghĩa tích lũy thô — nhưng vì biểu đồ vẽ dạng stacked area, tổng chiều cao tại mọi ngày bằng tổng work items đã được tạo ra (đã đi vào hệ thống) đến ngày đó.

-- EOD Snapshot cho CFD (theo project)

INSERT INTO cfd_daily_snapshot (

project_id, snapshot_date, state, item_count

)

SELECT

wi.project_id,

CURRENT_DATE,

wi.state,

COUNT(*) AS item_count

FROM work_items wi

WHERE wi.project_id = :projectId

AND wi.state IN (

'To Do', 'In Progress',

'Testing', 'Done'

)

GROUP BY wi.project_id, wi.state;

API trả về mảng (date, state, count). Frontend pivot thành dataset theo từng state để vẽ stacked area chart. Thứ tự stack từ dưới lên: Done → Testing → In Progress → To Do.

Logic phát hiện Bottleneck tự động

Backend chạy phân tích bottleneck định kỳ (mỗi ngày hoặc khi có thay đổi trạng thái). Thuật toán dựa trên độ tăng trưởng của dải màu theo thời gian:

// Pseudo-code — Bottleneck Detection

FOR EACH state IN ['In Progress', 'Testing']:

window = last N days snapshot

// Tính độ dốc tuyến tính (Linear Regression)

slope = linearSlope(window.dates, window.counts)


// Ngưỡng: slope > threshold → cảnh báo

IF slope > BOTTLENECK_THRESHOLD_PER_DAY:

alerts.push({

state: state,

slope: slope,

severity: slope > CRITICAL ? 'high' : 'medium'

})

Tham số khuyến nghị:

N = 5 ngày (sliding window) để loại bỏ nhiễu ngắn hạn.

BOTTLENECK_THRESHOLD_PER_DAY = 1.5 items/ngày.

CRITICAL = 3.0 items/ngày — hiển thị badge đỏ thay vì vàng.

Công thức độ dốc tuyến tính (OLS): slope = (N·Σxy − Σx·Σy) / (N·Σx² − (Σx)²)

Đặc tả cảnh báo văn bản (Alert Text Generation)

Severity: MEDIUM

"Dải trạng thái Testing đang phình to (+{slope} items/ngày trong 5 ngày qua). Có dấu hiệu tích tụ — kiểm tra năng lực QA."

Điều kiện: slope ∈ [1.5, 3.0)

Severity: HIGH (Bottleneck)

"Cảnh báo: Bottleneck nghiêm trọng tại trạng thái Testing (+{slope} items/ngày). Throughput bị chặn — cần hành động ngay."

Điều kiện: slope ≥ 3.0

Trạng thái bình thường

"Luồng công việc đang ổn định. Không phát hiện tích tụ bất thường ở bất kỳ trạng thái nào."

Điều kiện: tất cả slope < 1.5

Các chuỗi cảnh báo được lưu vào bảng project_alerts với TTL 24h và exposed qua API để Dashboard polling mỗi 5 phút.

Velocity Chart

Đo lường tốc độ đội ngũ & gợi ý Sprint kế tiếp

Định nghĩa dữ liệu từng cột

Cột Planned / Commit (màu xanh nhạt)

Tổng Story Points của tất cả User Story & Task được đưa vào Sprint tại thời điểm Sprint Planning kết thúc (event sprint.started). Giá trị này cố định sau khi Sprint bắt đầu và phản ánh cam kết ban đầu của đội.

planned_sp = SUM(story_points) WHERE sprint_id = X AND added_at <= sprint.start_date

Cột Completed (màu xanh lá)

Tổng Story Points của các User Story có state = 'Done'/'Closed' tại thời điểm Sprint Close (event sprint.closed). Chỉ tính Story Points của item hoàn toàn Done — item partially done không được tính.

completed_sp = SUM(story_points) WHERE sprint_id = X AND state IN ('Done','Closed') AND closed_date <= sprint.end_date

Công thức — Average Velocity & Dự báo Sprint kế tiếp

// 1. Average Velocity (N Sprint gần nhất)

AvgVelocity(N) = (1/N) × Σ completed_sp[i]

for i in last_N_closed_sprints


// 2. Weighted Average (tùy chọn — ưu tiên sprint gần)

weight[i] = i / Σ(1..N) // sprint mới nhất → weight cao nhất

WeightedAvgVelocity = Σ (completed_sp[i] × weight[i])


// 3. Gợi ý Capacity cho Sprint kế tiếp

SuggestedCapacity = round(AvgVelocity(N) × buffer)

// buffer = 0.85 (trừ hao 15% cho rủi ro mặc định)

Giá trị N khuyến nghị: 3–6 Sprint. Dưới 3 Sprint thì dữ liệu chưa đủ tin cậy — hiển thị cảnh báo "Cần thêm dữ liệu".

Luồng gợi ý tự động khi PM tạo Sprint mới

Bước 1 — PM tạo Sprint

PM nhấn "New Sprint" → hệ thống trigger API GET /velocity/suggestion?projectId=X.

Bước 2 — Tính toán

Backend lấy N=3 Sprint đã Close gần nhất, tính AvgVelocity và nhân hệ số buffer=0.85.

Bước 3 — Trả về response

{ suggested_sp: 34,
  avg_velocity: 40,
  based_on_sprints: 3,
  confidence: "medium" }

Bước 4 — Hiển thị UI

Form Sprint Planning hiển thị chip "Gợi ý: 34 SP (dựa trên 3 sprint gần nhất)". PM có thể giữ nguyên hoặc điều chỉnh.

Confidence: LOW

Số Sprint closed < 3 — hiển thị cảnh báo, gợi ý không bật tự động.

Confidence: MEDIUM

3–5 Sprint closed — gợi ý hiển thị với nhãn "Tham khảo".

Confidence: HIGH

≥ 6 Sprint closed — gợi ý hiển thị mặc định, PM chỉ cần confirm.
